# 검토 메모 저장 형식

검토 메모는 원본 Markdown 끝의 예약 HTML 주석에 JSON으로 저장한다. 이 문서는 [`review-source.mjs`](../../src/content/review-source.mjs)의 현행 저장 형식과 [`file-writer.mjs`](../../src/content/file-writer.mjs)의 저장 경계를 설명한다. 기능 범위는 [지원 기능](../../README.ko.md#주요-기능), 사용 절차는 [로컬 설치와 사용](../operations/local_install.md#체크박스와-메모-검토)을 따른다.

## 구역과 버전

저장 구조는 `본문 + separator + 시작 마커 + JSON + 끝 마커 + 후행 공백`이다. 시작 마커는 `<!-- MARKDOWN-LEADER:NOTES:START`, 끝 마커는 `MARKDOWN-LEADER:NOTES:END -->`이며 대소문자를 구분한다. 메모 주석은 들여쓰기 없는 최상위 블록으로 문서 끝에 하나만 둔다. 끝 마커 뒤에는 공백 문자만 허용한다.

다음은 본문이 `검토할 문장입니다.`일 때 생성되는 원문이다. 코드 블록 안의 마커는 형식 설명용이며 실제 메모로 읽지 않는다.

```markdown
검토할 문장입니다.

<!-- MARKDOWN-LEADER:NOTES:START
{
  "version": 1,
  "separator": "\n\n",
  "notes": [
    {
      "id": "n1",
      "quote": "검토할 문장",
      "prefix": "",
      "suffix": "입니다.",
      "heading": "",
      "text": "표현을 확인해 주세요.",
      "createdAt": "2026-09-10T00:00:00.000Z"
    }
  ]
}
MARKDOWN-LEADER:NOTES:END -->
```

| 최상위 필드 | 현행 계약 |
|---|---|
| `version` | 숫자 `1`만 읽는다. 제품 버전과 별개인 저장 형식 버전이다. |
| `separator` | `\n\n`, `\r\n\r\n`, `\r\r` 중 하나인 문자열. 주석 바로 앞의 실제 문자와 일치해야 한다. |
| `notes` | 아래 필드를 가진 메모 객체의 배열. 빈 배열도 파서는 허용하지만, 저장 함수에 빈 배열을 넘기면 메모 구역을 제거한다. |

`separator`는 메모 구역을 붙일 때 추가한 두 줄바꿈을 식별한다. 삭제 시 이 부분만 제거하므로 기존 본문의 마지막 줄바꿈과 구분할 수 있다. 현재 구현에는 다른 버전으로부터의 마이그레이션이 없다.

## 메모 필드와 본문 연결

모든 메모는 다음 일곱 필드를 문자열로 가져야 한다.

| 필드 | 의미와 현재 UI 생성 방식 |
|---|---|
| `id` | 메모 식별자. 빈 문자열과 배열 내 중복을 거부한다. UI는 `crypto.randomUUID()`로 생성한다. |
| `quote` | 선택한 렌더링 본문 텍스트. Markdown 소스 위치나 행 번호가 아니다. |
| `prefix` | 선택 범위 앞의 텍스트. UI는 최대 64 UTF-16 코드 단위를 저장한다. |
| `suffix` | 선택 범위 뒤의 텍스트. UI는 최대 64 UTF-16 코드 단위를 저장한다. |
| `heading` | 선택 시작점이 속하거나 그보다 앞에 있는 마지막 제목의 텍스트. 해당 제목이 없으면 빈 문자열이다. |
| `text` | 사용자가 작성한 메모 내용. |
| `createdAt` | 생성 시각. UI는 `new Date().toISOString()` 결과를 저장한다. |

형식 검증은 필드의 문자열 여부와 `id`의 비어 있지 않음·중복 여부를 검사한다. UUID 형식, 날짜 형식, 문맥 길이, `id` 외 필드의 빈 문자열은 검증하지 않는다. 알 수 없는 추가 필드도 거부하지 않지만, 이를 확장 계약이나 향후 보존 보장으로 해석하지 않는다.

본문 연결은 [`review-ui.mjs`](../../src/content/review-ui.mjs)의 `locateReviewQuote()`가 담당한다. 인용문이 한 곳에 있으면 그 위치를 사용하고, 여러 곳에 있으면 앞뒤 문맥으로 유일하게 일치하는 위치를 찾는다. `heading`은 현재 위치 검색에 사용하지 않는다. 대상이 없거나 모호하면 메모 데이터는 유지하고 본문 연결을 표시하지 않는다. 화면의 메모 번호는 저장 필드가 아니다.

## 읽기·쓰기 검증

- `parseReview(raw)`는 `{ body, notes }`를 반환한다. 메모 뒤에 공백이 있으면 `trailing`도 반환한다. 예약 메모 주석이 없으면 원문 전체를 `body`로 유지한다.
- Markdown 주석으로 인식한 `MARKDOWN-LEADER:NOTES:` 구역이 중복되거나 인라인에 있으면 거부한다. 마커 손상, JSON 오류, 지원하지 않는 버전, 잘못된 필드·구분자, 구역 뒤의 일반 본문도 거부한다. 주요 형식 오류에는 `review-invalid` 코드를 사용한다.
- 코드 펜스 안의 마커는 메모가 아니다. `writeReview(raw, notes)`는 결과를 다시 읽어 메모 개수를 확인하므로, 닫히지 않은 코드 펜스가 새 구역을 삼키는 원문에는 메모를 저장하지 않는다.
- `writeReview()`는 기존 구역을 먼저 검증한다. 본문과 후행 공백은 유지하고 메모 JSON은 들여쓰기 2칸으로 다시 직렬화한다. 기존 JSON의 공백·필드 배치까지 원문 그대로 보존하는 함수는 아니다.
- 새 구역의 줄바꿈은 본문에서 처음 발견한 CRLF·CR·LF를 사용하며, 본문에 줄바꿈이 없으면 LF를 사용한다. 본문 전체의 줄바꿈을 통일하지 않는다.
- JSON의 `<`, `>`, `&`는 각각 `\u003c`, `\u003e`, `\u0026`으로 이스케이프한다. 메모의 `-->` 등이 주석을 조기에 닫지 않도록 하며, JSON을 읽으면 원래 문자열로 복원된다.
- 마지막 메모를 삭제하면 예약 구역과 그 구분자를 제거한다. 본문의 BOM·마지막 줄바꿈과 메모 구역 뒤에 외부 편집기가 추가한 공백은 유지한다.

체크박스는 메모 배열에 저장하지 않는다. `patchTask(raw, line, checked)`는 실제 Markdown 목록의 작업 항목인지 확인하고, 0부터 시작하는 소스 행에서 `[ ]`·`[x]`·`[X]`의 가운데 한 글자만 바꾼다. 코드·표의 유사 문구는 변경하지 않는다.

## 실제 파일 저장과 제한

`writeReview()`와 `patchTask()`는 문자열만 만든다. 실제 파일 저장은 `index.ts`의 `saveDocumentRevision()`이 문서 상태를 확인한 뒤 `writeFileRevision()`에 요청한다.

1. 현재 문서·기대 원문과 진행 중인 저장 여부를 확인한다. 파일 핸들이 없으면 사용자에게 현재 원본 파일을 선택하도록 안내한다.
2. writer가 `readwrite` 권한을 확인하고 필요하면 요청한다. 같은 모듈 인스턴스에서 같은 핸들 또는 `isSameEntry()`로 같은 파일임을 확인한 저장은 순서대로 처리한다.
3. 파일을 UTF-8로 엄격하게 읽어 기대 원문과 비교한다. 최초 비교에서는 선두 BOM 유무만 무시한다. UTF-8로 읽을 수 없는 파일은 저장하지 않는다.
4. `createWritable({ mode: 'exclusive' })` 호출 뒤와 쓰기 뒤에 원본을 다시 읽어 변경 여부를 검사한다. 각 단계에서 호출자가 전달한 `isCurrent()`로 문서 전환 등 오래된 작업도 검사한다.
5. 원본의 BOM 유무를 유지한 UTF-8 데이터를 쓰고 `close()`를 호출한다. 스트림을 연 뒤 오류가 나면 `abort()`를 시도하고 오류를 전달한다.

기대 원문과 다르면 `file-conflict`, 현재 작업이 아니면 `file-stale`, 쓰기 권한이 거부되면 `file-permission` 오류를 사용한다. 파일 API 자체의 오류도 호출자에게 전달한다.

이 검사는 외부 편집기와의 모든 동시 저장을 막는 보장이 아니다. 마지막 비교와 `close()` 사이에도 외부 변경이 생길 수 있고, 메모 병합·충돌 자동 복구·백업 기능은 없다. 파일 URL로 연 문서에 핸들을 다시 연결할 때도 파일명과 내용은 확인하지만 절대 경로의 동일성은 증명하지 못한다. 같은 이름·내용을 가진 다른 파일을 선택하지 않도록 원본 경로를 직접 확인해야 한다.

## 검증 기준

프로젝트 루트에서 다음 명령으로 저장 형식·원문 보존·충돌 처리의 단위 테스트를 실행한다.

```powershell
node --test tests/review-source.test.mjs tests/file-writer.test.mjs
```

파일 writer 테스트는 가짜 파일 핸들로 호출 순서와 실패 처리를 검사한다. 실제 OS 선택창·디스크 저장 검증 결과는 [개발 안내](../operations/local_install.md#개발-검증)을 별도로 확인한다. 다른 Markdown 리더나 AI 도구가 이 JSON을 자동으로 지원한다는 호환성 보장은 없다.
